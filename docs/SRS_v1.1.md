# 1. 引言与目标

## 1.1 背景

现有本地明棋实现已经能够运行，但规则正确性、模拟器吞吐、搜索质量、训练平台期和版本间棋力变化尚缺少统一的可视化验证与量化基线。本项目不把“继续增加环境步数”视为默认解决方案，而是先建立一个可信、可测、可复现的平台，使任何性能或棋力改动都能被定位。

## 1.2 核心目标

- 规则可信：所有合法移动、战斗、终局与重复规则均由独立 RuleProfile
  驱动，并可在 GUI 中逐步解释。

- 调试可视：支持摆局、合法着高亮、非法原因、单步执行、撤销、回放、状态哈希和规则事件查看。

- AI 可插拔：同一 GUI
  能加载手工策略、Alpha-Beta、MCTS、神经网络或外部进程引擎。

- 性能可量化：把
  make/unmake、着法生成、静态评估、搜索节点和网络推理分别基准测试。

- 棋力可证明：使用固定局面集、配对开局、历史版本池、置信区间与
  SPRT，而非只看训练自博弈 Elo。

- 训练可诊断：数据生成、去重、采样和模型版本全部可追溯；长期平台期可以被拆成搜索教师、表示、数据分布或训练问题。

- 自动改进可扩展：保留“代码候选生成—自动评测—种群选择—人工晋升”的演化闭环，使启发式、搜索参数、局面特征和受控代码模块可以被自动探索。

## 1.3 非目标

- 本版本不实现暗棋、不完全信息信念搜索或 ReBeL。

- 本版本不实现四国军棋、组队通信或多人非零和规则。

- 不对第三方游戏平台进行客户端注入、内存读取、抓包或自动化作弊。

- 不要求首个版本即达到顶尖人类水平；要求建立可验证的持续提升闭环。

- 不把具体神经网络框架、搜索算法写死为唯一实现。

- P0/P1 基线不要求实现完整自主代码演化服务；但架构、文件格式和评测器必须允许后续加入 AlphaEvolve 式扩展。

# 3. 术语、角色与使用场景

## 3.1 术语

| **术语**     | **定义**                                                                  |
|--------------|---------------------------------------------------------------------------|
| 明棋         | 双方从初始时刻起均可见全部棋子身份的二人军棋。                            |
| 半回合 / ply | 单方执行一次合法移动。                                                    |
| 局面 State   | 棋盘占用、棋子身份/存活、行棋方、历史相关状态和规则配置的完整确定性状态。 |
| 动作编码空间 | 可容纳所有 from-to 组合的固定编号空间；不等于实际合法分支数。             |
| 实际分支数   | 某一状态中由规则核直接生成的合法着数量。                                  |
| RuleProfile  | 对棋盘拓扑、棋子、布阵、移动、战斗、终局、重复和时间控制的版本化配置。    |
| 引擎 Engine  | 给定状态和限制后返回走法、分析或策略分布的可插拔 AI。                     |
| PV           | Principal Variation，搜索器认为的主变化序列。                             |
| NPS          | Nodes Per Second，搜索节点吞吐。                                          |
| TT           | Transposition Table，置换表。                                             |
| 配对对局     | 同一初始局面交换先后手或阵营进行两局，以降低开局和先手偏差。              |
| 自动演化     | 由提议器生成代码或配置候选，经可信评测器自动筛选、保留和组合的迭代优化过程。 |
| 候选 Candidate | 一份不可变的代码补丁、配置、构建产物及完整谱系元数据。                  |
| 评测器 Evaluator | 不受候选控制的可信程序，负责正确性、性能、棋力、稳健性与资源评分。      |

## 3.2 用户角色

| **角色**    | **主要任务**                                 |
|-------------|----------------------------------------------|
| 规则开发者  | 维护 RuleProfile、规则核和回归测试。         |
| AI 开发者   | 实现引擎、搜索、估值、网络推理和训练。       |
| 测试者/棋手 | 通过 GUI 摆局、对弈、查看规则和评价棋力。    |
| 实验管理员  | 配置批量比赛、基准硬件、模型版本和统计报告。 |
| 维护者      | 发布版本、迁移记录、管理兼容性和故障日志。   |
| 演化管理员  | 配置可变代码边界、评测预算、种群策略，并审核候选晋升。 |

## 3.3 关键使用场景

- UC-01：在编辑器中摆出一个边界局面，点击棋子后查看全部合法目标格，并检查某个目标为何非法。

- UC-02：人类与指定 AI 对弈；随时暂停、撤销、请求分析或切换到自动播放。

- UC-03：加载历史记录，逐步查看每一手前后的状态、战斗结果、局面哈希与引擎思考信息。

- UC-04：让两个引擎在同一布局池中进行配对比赛，生成胜率、Elo、置信区间和异常对局列表。

- UC-05：运行规则核微基准和搜索基准，定位平台期究竟来自模拟器、搜索、推理还是数据管线。

- UC-06：批量生成搜索教师标签，保存可复现的数据清单，并用新模型进行固定预算回归。

- UC-07：在 Evolution Lab 中选择种子引擎和可变模块，运行候选生成与分层评测，查看代码差异、谱系、失败原因和 Pareto 前沿，并人工批准晋升。

# 4. 规则模型与默认 RuleProfile

## 4.1 原则

军棋在线下与不同平台之间可能存在重复、和棋、进入大本营、时间控制等细节差异。因此，规则核必须读取版本化
RuleProfile；GUI
必须在对局标题、记录文件和分析面板中显示当前配置标识。任何未写入
RuleProfile 的“隐含规则”都视为缺陷。

## 4.2 默认棋盘与棋子集合

| **类别** | **默认配置**                                                                                               |
|----------|------------------------------------------------------------------------------------------------------------|
| 棋盘     | 5 × 12，共 60 个格点；道路、铁路、行营和大本营按拓扑图描述，不在代码中依赖坐标特判。                       |
| 每方棋子 | 司令 1、军长 1、师长 2、旅长 2、团长 2、营长 2、连长 3、排长 3、工兵 3、炸弹 2、地雷 3、军旗 1，共 25 枚。 |
| 可见性   | 明棋模式：双方和观察者始终可见全部身份。                                                                   |
| 胜负     | 默认以夺取军旗或对方无任何合法着为胜；重复、步数上限和超时行为由 RuleProfile 指定。                        |

## 4.3 默认规则语义（可配置）

| **规则项**   | **默认语义**                                                                                |
|--------------|---------------------------------------------------------------------------------------------|
| 棋子普通移动 | 普通道路每次沿相邻连线移动一格；不得跨越占用格。                                            |
| 铁路移动     | 非工兵沿同一直线铁路移动任意空距，不得穿越棋子；工兵可沿连通铁路转弯，路径中间格必须为空。  |
| 行营         | 默认行营内棋子不可被攻击；空行营可按棋盘连线进入。该行为必须可配置。                        |
| 大本营       | 默认进入大本营的棋子不可再移动；军旗只能位于己方大本营。该行为必须可配置。                  |
| 等级比较     | 普通军阶按司令至工兵由高到低比较；高者存活，低者移除；同级双方移除。                        |
| 炸弹         | 与任意可攻击棋子交战时双方移除；与地雷的具体处理由战斗矩阵明确给出。                        |
| 地雷         | 默认战胜除工兵与炸弹外的攻击者；工兵攻击地雷时工兵存活、地雷移除。                          |
| 军旗         | 被任意可攻击棋子成功进入所在格时，军旗方立即失败。                                          |
| 重复/停滞    | 默认使用可配置的重复次数、无吃子步数或最大 ply 上限判和；规则核保存实现判定所需的最小历史。 |

| **规则冻结要求：**在开始训练或正式版本对战前，必须导出当前 RuleProfile 的规范化文本与 SHA-256。记录文件只引用哈希而无法还原规则时，不得作为长期基准数据。 |
|-----------------------------------------------------------------------------------------------------------------------------------------------------------|

# 5. 总体架构

## 5.1 分层结构

| **Desktop GUI / CLI / Tournament Controller / Evolution Lab** |
|----------------------------------------------------------------|
| **Evolution Orchestrator + Trusted Evaluators + Sandbox**       |
| **Engine Host（进程隔离、超时、协议、日志）**                  |
| **AI Engines（Random / Heuristic / Alpha-Beta / MCTS / NN）**  |
| **Search SDK（TT、排序、评估、批量推理接口）**                 |
| **Rule Core API（movegen、apply/undo、terminal、hash）**       |
| **Immutable RuleProfile + BoardTopology**                      |
| **Persistence（records、datasets、reports、configs、lineage）**|

## 5.2 架构约束

| **需求 ID** | **优先级** | **要求与验收标准**                                                                                |
|-------------|------------|---------------------------------------------------------------------------------------------------|
| AR-001      | P0         | Rule Core 必须为无 GUI、无 Python、无网络依赖的独立库；同一状态和动作在所有前端得到完全相同结果。 |
| AR-002      | P0         | RuleProfile 在一局开始后不可变；新局才可切换配置。                                                |
| AR-003      | P0         | 搜索热路径不得依赖字符串、JSON、日志 I/O 或堆分配。                                               |
| AR-004      | P0         | GUI 不得自行复制规则逻辑；合法着、战斗预览、终局均调用 Rule Core。                                |
| AR-005      | P0         | 外部 AI 默认使用独立进程协议，单个引擎崩溃不得导致 GUI 或比赛控制器崩溃。                         |
| AR-006      | P1         | 提供稳定 C ABI 或薄 C++ API，并提供 Python 绑定；Python 层不参与单节点 make/unmake 热路径。       |
| AR-007      | P1         | 神经网络推理器与搜索器解耦，支持本地同步、批量异步和模拟推理后端。                                |
| AR-008      | P1         | 自动演化模块只能修改白名单路径；Rule Core、规则测试、评测器、隐藏测试和正式比赛控制器必须只读。       |
| AR-009      | P1         | 候选构建和运行必须在资源受限沙箱中执行；默认禁用网络访问，并限制 CPU、GPU、内存、磁盘与运行时间。       |
| AR-010      | P1         | 自动生成候选不得自动覆盖正式引擎；晋升必须产生签名报告并经过显式人工批准。                            |

## 5.3 推荐线程模型

- GUI 主线程：仅负责界面和命令派发，不执行长搜索。

- 每个交互引擎一个工作线程或独立进程；支持 stop token。

- 批量比赛使用固定大小 worker pool，每局拥有独立 State，不共享可变局面。

- 神经网络推理可由集中式 batch server 聚合多个搜索器的叶子请求。

- 日志使用异步队列，但关键对局记录必须在局终止时原子落盘。

- Evolution Orchestrator 使用独立作业队列；候选构建、评测和比赛 worker 与 GUI/正式比赛池隔离。

# 6. 核心数据模型与文件格式

## 6.1 State 与 UndoRecord

```cpp
State {

RuleProfileId rules;

Player side_to_move;

PieceOnSquare board[60];

SquareOfPiece piece_square[50];

AliveMask alive[2];

HistoryState history; // repetition / no-capture / ply

ZobristKey key;

}

Move { uint8 from; uint8 to; uint16 flags; }

UndoRecord { captured_piece; prior_history; prior_key_delta; ... }
```

实现可以采用更紧凑的位布局，但对外语义必须等价。PieceId
在整局中稳定，不因移动或被吃而复用。

## 6.2 状态不变量

- 每个存活棋子恰好位于一个格点；每个格点至多一个棋子。

- 棋子类型、阵营和 PieceId 在整局中不可改变。

- 增量哈希必须与从零重算哈希一致。

- apply(move) 后 undo(record) 必须逐字节恢复规范化状态。

- 历史状态必须足以独立判断 RuleProfile
  所定义的重复、无吃子和最大步数规则。

## 6.3 对局记录格式

长期存储使用自描述
JSON（便于审计），高吞吐数据可使用二进制分片，但必须配套 manifest
和转换工具。

```json
{

"format": "junqi-open-record-v1",

"rule_profile_sha256": "...",

"initial_state": "base64-or-structured",

"players": [{"engine":"ab_v12","side":"red"},
{"engine":"human","side":"blue"}],

"seed": 123456789,

"moves": [

{"ply":0,"from":51,"to":46,"key_before":"...","key_after":"...",

"event":{"type":"MOVE","combat":null},
```

系统必须把“变弱或不再提升”拆成可观测指标。至少输出：

- 更深搜索对更浅搜索的配对胜率；若深度增加不变强，优先审计规则、估值、排序和剪枝。

- 历史版本 cross-play 矩阵，用于发现循环克制和仅对最新版过拟合。

# 11. 功能需求：自动演化与算法发现

## 11.1 定位与原则

本模块保留一种类似 AlphaEvolve 的可能性：由一个或多个提议器生成代码/配置候选，可信评测器执行自动验证和评分，演化控制器维护种群、谱系与精英档案，再把高质量候选送入更昂贵的比赛与人工审核。它是平台的可选扩展，不得成为规则正确性的依赖。

必须遵守以下原则：

1. **规则不可演化**：Rule Core、RuleProfile、BoardTopology、战斗矩阵和合法性判定不属于候选搜索空间。
2. **评测器不可演化**：候选不得读写或替换测试、隐藏布局、统计器、比赛控制器和评分脚本。
3. **先约束后放开**：首版优先演化参数和 DSL 表达式，随后才允许修改白名单 C++/Python 文件。
4. **多目标而非单指标**：正确性是硬门禁；棋力、速度、内存、代码复杂度和稳健性使用 Pareto 档案或分层评分。
5. **所有结果可复现**：任何候选必须能够由父代、补丁、提议器版本、随机种子、工具链和评测配置重建。
6. **候选不自动上线**：正式引擎只能由人工批准的已签名候选生成。

## 11.2 可演化对象与保护边界

### 允许的候选目标

| 级别 | 可演化对象 | 推荐启用阶段 |
|---|---|---|
| E0 | 搜索参数、时间分配、LMR 表、aspiration 窗口、启发式权重。 | 首版 |
| E1 | 受限表达式 DSL：静态估值特征组合、走法排序打分、局面阶段分类。 | 首版 |
| E2 | 白名单 C++ 模块：廉价估值、排序器、选择性延伸、候选剪枝条件。 | 正确性门禁成熟后 |
| E3 | 数据采样器、战术局面生成器、训练超参数和小型网络结构配置。 | 训练闭环稳定后 |
| E4 | 新搜索算法或多模块补丁。 | 研究模式；默认关闭 |

### 永久只读对象

- `/rule_core/**`、`/config/rules/**`、`/tests/rules/**`；
- 参考 movegen、参考 minimax、记录重放验证器；
- 评测器、统计器、隐藏测试、正式布局池和正式历史对手池；
- 候选 ID、父代谱系、资源计量和审计日志；
- 发布签名与正式引擎目录。

候选若尝试越界写入、动态加载未批准库、访问网络或读取隐藏测试路径，必须立即终止并标记为 `SANDBOX_VIOLATION`。

## 11.3 演化循环

标准循环如下：

```text
种子种群 / 精英档案
        ↓
提议器生成补丁或配置候选
        ↓
规范化、去重、静态检查和沙箱构建
        ↓
正确性门禁
        ↓
微基准与固定题集筛选
        ↓
小规模配对比赛
        ↓
隐藏布局、历史池与鲁棒性评测
        ↓
更新 Pareto 档案、种群和谱系
        ↓
人工审核后晋升为实验引擎或正式引擎
```

提议器可以是 LLM、模板变异、贝叶斯优化、遗传编程、CMA-ES、人工补丁或其组合。系统不得依赖某一家模型 API；提议器通过统一接口工作。

## 11.5 分层评测门禁

评测按成本从低到高执行；任一硬门禁失败后，默认不进入后续阶段。

| 阶段 | 必须执行的评测 | 典型淘汰原因 |
|---|---|---|
| G0 结构 | 白名单路径、补丁大小、依赖和危险 API 检查。 | 越界修改、网络访问、修改评测器。 |
| G1 构建 | 多编译器警告、静态分析、ASan/UBSan 或等价检测。 | 编译失败、未定义行为、泄漏。 |
| G2 正确性 | 规则回归、apply/undo、哈希、参考 movegen、深度受限 minimax 差分。 | 非法着、错误剪枝、状态损坏。 |
| G3 性能 | movegen、make/undo、eval、固定深度搜索、内存峰值。 | 吞吐下降超限、内存失控。 |
| G4 局面质量 | 战术题、残局、搜索稳定性、深浅搜索一致性。 | 题集退化、分数漂移。 |
| G5 快速棋力 | 对基线和父代进行小规模配对比赛。 | 明显弱于父代或错误率升高。 |
| G6 完整棋力 | 历史池、布局池、隐藏集、多个预算与随机种子。 | 过拟合单一对手或单一布局。 |
| G7 晋升 | SPRT/置信区间、人工代码审查、长期压力测试。 | 提升不显著、不可解释风险。 |

正确性、沙箱和资源上限是硬约束，不能通过更高棋力抵消。

## 11.6 评分、选择与防止过拟合

系统应优先维护 Pareto 前沿，而不是只使用一个易被钻空子的总分。至少考虑：

- 对正式版本和历史池的配对得分率及置信下界；
- 固定节点、固定时间和固定推理次数下的棋力；
- 战术/残局正确率与 value calibration；
- NPS、评估吞吐、内存峰值和二进制大小；
- 崩溃、超时、非法着和非确定性错误率；
- 代码复杂度、修改行数和新增依赖。

可使用下式作为初筛分数，但不得替代硬门禁和 Pareto 记录：

$$
S = w_E E_{\mathrm{LCB}} + w_T T + w_P \log(P/P_0)
    - w_M \log(M/M_0) - w_C C - w_R R,
$$

其中 $E_{\mathrm{LCB}}$ 为棋力提升置信下界，$T$ 为题集得分，$P$ 为吞吐，$M$ 为内存，$C$ 为复杂度惩罚，$R$ 为错误与不稳定惩罚。

防过拟合要求：

- 提议器不可访问 G6/G7 隐藏测试内容，只能得到聚合得分和有限失败分类；
- 公开训练布局与隐藏验收布局分离，定期轮换隐藏集版本；
- 至少使用多个随机种子、多个时间/节点预算和多类布局；
- 对历史引擎池进行 cross-play，不允许只针对当前父代优化；
- 对可疑大幅提升候选执行独立重跑和人工审查；
- 被淘汰候选可保留为“反例档案”，用于后续提议器避免重复错误。

## 11.8 Evolution Lab GUI

GUI 应提供独立的 Evolution Lab，不与普通对局界面混合。至少包含：

- 实验配置：种子引擎、可变级别 E0-E4、提议器、预算、种群大小、评测配置；
- 实时队列：候选当前门禁、已用资源、预期后续阶段、取消/暂停；
- 候选详情：代码 diff、父代、提议理由、构建日志、失败原因、指标和对局回放；
- 谱系图：种群、精英、交叉和淘汰关系；
- Pareto 视图：棋力—速度—内存—复杂度的非支配候选；
- 对比工具：候选与父代在同一局面上的评估、排序、PV 和首个分歧；
- 晋升工作流：拒绝、保留为精英、加入实验池、申请正式发布；
- 安全状态：沙箱策略、只读路径、隐藏评测版本和任何越界事件。

## 11.9 提议器与评测器接口

```cpp
struct CandidateProposal {
    CandidateId id;
    std::vector<CandidateId> parents;
    NormalizedPatch patch;
    ProposalMetadata metadata;
};

class CandidateProposer {
public:
    virtual CandidateProposal propose(
        const EvolutionContext& context,
        const PopulationSnapshot& population,
        RandomSeed seed) = 0;
};

class TrustedEvaluator {
public:
    virtual GateResult evaluate(
        const CandidateArtifact& candidate,
        GateId gate,
        const ResourceBudget& budget) = 0;
};
```

提议器只能获得 `EvolutionContext` 中明确公开的信息。`TrustedEvaluator` 不得加载候选提供的评分代码。

## 11.10 晋升规则

候选进入正式版本前必须同时满足：

1. G0-G7 全部必需门禁通过；
2. 规则与记录回归 100% 通过；
3. 在预设统计检验下相对正式版本达到所需提升，或在棋力不降的前提下达到明确性能收益；
4. 隐藏布局、多个预算和历史池中未发现集中退化；
5. 代码差异经过人工审查，新增复杂度和依赖可接受；
6. 生成冻结的源码、配置、二进制、完整报告与签名 manifest；
7. 由具备权限的维护者显式批准。

任何候选不得仅凭公开题集最高分或单轮自博弈 Elo 自动晋升。

## 12.4 发布门槛

- 规则与记录兼容性测试 100% 通过。

- 无新增非法着、崩溃或不可复现对局。

- 固定预算下对当前正式版本达到预设统计门槛；若只优化性能，则棋力不得显著下降。

- 搜索优化必须在“安全模式 vs 优化模式”的随机小局面深搜比较中无已知错误。

- 性能回归超过 5% 必须解释；超过 10% 默认阻止发布。

# 14. 测试与验收计划

## 14.1 测试层次

| **层次** | **方法**                   | **代表性内容**                                      |
|----------|----------------------------|-----------------------------------------------------|
| 单元测试 | 确定输入/输出断言。        | 战斗矩阵、道路、铁路、行营、大本营、终局。          |
| 属性测试 | 随机生成局面和动作。       | generate 与 check 一致；apply/undo 可逆；哈希一致。 |
| 差分测试 | 安全参考实现 vs 优化实现。 | 合法着集合、终局、深度受限 minimax。                |
| GUI 测试 | 人工脚本 + 自动 UI。       | 摆局、非法提示、回放、引擎取消、缩放。              |
| 压力测试 | 长时批处理。               | 泄漏、死锁、崩溃恢复、断点续跑。                    |
| 棋力测试 | 配对比赛与固定题集。       | 搜索增益、版本提升、非传递性。                      |

## 14.2 必做规则测试

- 每种棋子在普通道路、铁路、行营、大本营边界上的可移动与不可移动例。

- 铁路中间有己方/敌方阻挡、直线拐弯、工兵多次转弯、不可达铁路连通分量。

- 所有棋子类型两两战斗矩阵；同级、炸弹、地雷、工兵和军旗。

- 行营受保护开关、大本营禁出开关的正反配置。

- 夺旗、无合法着、重复、无吃子上限、最大 ply 和时间控制的优先级。

- 执行非法着前后状态完全不变；执行合法着后撤销逐字段一致。

| **需求 ID** | **优先级** | **要求与验收标准**                                                              |

| AT-002      | P0         | 随机选择合法着 apply 后立即 undo，规范化状态字节必须完全一致。                  |
| AT-003      | P0         | 对随机小局面，以慢速参考铁路 BFS 与优化 movegen 比较合法着集合。                |
| AT-004      | P0         | 对小深度随机局面，安全 Alpha-Beta 与无剪枝 minimax 的分数和最佳着集合一致。     |
| AT-005      | P1         | 对记录文件进行截断、字段缺失、错误哈希和未知版本模糊测试，程序不得崩溃。        |

## 14.5 性能基准方法

- 固定编译器、Release 配置、CPU 亲和性和单线程；预热后测量至少 5
  次，报告中位数和 P95。

- 使用开局、中局高分支、铁路密集、战斗密集和残局五类状态，不只测随机局面。

- 分别测量：空循环、状态复制、make/undo、movegen、terminal、incremental
  eval、完整搜索和 NN batch。

- 搜索报告同时给出实际展开节点和网络评估次数，避免把“1000
  搜索节点”错误等同于“1000 次完整环境步”。

- 所有基准命令、状态集和结果 JSON 纳入版本控制或报告归档。

## 15.3 现有本地项目迁移策略

1.  第一步不是重写，而是给现有 State、legal moves 和 step
    外包一层稳定接口，并建立记录回放。

2.  先同时保留“慢速参考实现”和“现有快速实现”，通过差分测试找规则差异。

3.  GUI 首版只依赖参考接口，确认规则后再接入优化内核。

4.  把现有 RL 模型包装为
    Engine；禁止它直接访问内部可变状态或跳过合法校验。

5.  以固定模型为基准，分别替换 movegen、state update、search
    和训练数据，测量每次改动的独立效果。

# 16. 风险、约束与后续扩展

## 16.1 主要风险与缓解

| **风险**         | **表现**                      | **缓解措施**                                           |
|------------------|-------------------------------|--------------------------------------------------------|
| 规则语义不一致   | GUI、搜索、训练各有一套规则。 | Rule Core 单一事实来源；RuleProfile 哈希；记录重放。   |
| 性能优化引入错解 | 剪枝/缓存后棋力异常。         | 安全模式、差分搜索、随机小局面穷举。                   |
| 合法动作空间误解 | 把 3600 编码位都当分支。      | 直接 movegen；报告实际分支数分布。                     |
| 训练平台期       | 10M 步后不再提升。            | 搜索增益、固定题集、数据多样性和 cross-play 分拆诊断。 |
| 自博弈循环克制   | 新版本只胜当前对手。          | 历史策略池、cross-play、多个基线。                     |
| GPU 推理瓶颈     | 每节点单样本调用。            | 小网络、批量叶子、评估次数单独计量。                   |
| GUI 阻塞         | 搜索导致界面无响应。          | 进程/线程隔离、可取消请求、request_id。                |
| 数据不可复现     | 模型强弱原因无法追溯。        | 完整 manifest、代码/规则/模型/种子记录。               |
| 评测器被钻空子   | 候选通过改测试、读隐藏集或利用单一指标获得虚假高分。 | 只读可信评测器、隐藏集、硬门禁、Pareto 与人工晋升。 |
| 演化过拟合       | 只对父代、公开布局或固定预算有效。 | 历史池、多预算、隐藏布局、独立复跑和反例档案。 |
| 候选代码不安全   | 越界文件访问、资源耗尽或未批准依赖。 | 无网络沙箱、资源上限、白名单路径和静态检查。 |

## 16.2 后续扩展接口

- 暗棋：新增 Observation、Belief 与私有状态，但复用 Rule
  Core、GUI、记录、引擎 Host 和明棋叶子估值。

- 残局求解器：引入 retrograde 数据库与精确 WDL/DTW 标签。

- 分布式训练：把数据生成 worker
  和批量推理服务替换为远程实现，不改变记录语义。

- 网页观察器：只读复用记录和分析协议，不复制规则逻辑。

- 规则变体：增加新 RuleProfile
  和测试集，而不是在代码中添加无版本条件分支。

- 自动演化深化：从 E0/E1 参数与 DSL 演化，逐步开放到 E2/E3；E4 始终作为受控研究模式。
